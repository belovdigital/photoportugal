# Предметная область — инварианты продукта

Что здесь: правила, которые делают продукт этим продуктом. Не архитектура
(`ARCHITECTURE.md`), не карта серверов (`MARKETS.md`), не история инцидентов
(память Клода). Сюда попадает то, что нельзя вывести из кода за пять минут, но
что ломает деньги или доверие, если понять неправильно.

**Пометки:** `✔код` — проверено в коде, ссылка рядом. `✔прод` — проверено
запросом к боевой базе 14.08.2026. `❓` — я не смог установить, нужен ответ
Алекса; такие пункты собраны в §9.

**Правило поддержки:** инвариант меняется — правится этот файл в том же
коммите. Документ, который отстал, хуже отсутствующего: по нему принимают
решения. Если пункт устарел и лень чинить — удалить пункт.

## 1. Что это

Маркетплейс фотографов для путешественников. Клиент выбирает фотографа под
город, дату и повод, платит на площадке, получает галерею. Фотограф платит
подписку и комиссию с брони.

Один репозиторий обслуживает **три независимых рынка** — PT, ES, IT. Общая
ровно одна вещь: код. Базы, домены, Stripe-аккаунты, письма, локали — разные.
Карта в `MARKETS.md §2`. Практическое следствие: **любая правка ради одного
рынка прилетает остальным**, и это главный источник «починили тут, сломали там».

Роли: `client`, `photographer`, `admin` (`users.role`). На PT — 164 / 94 / 1
(`✔прод`).

## 2. Деньги — три разных числа

Самое важное в проекте. Одна база даёт **три** суммы, и путать их нельзя.

| Число | Что это | Кто видит |
|---|---|---|
| **base** | цена пакета, как её задал фотограф | **никто из двоих** |
| **all-in** | что платит клиент | только клиент |
| **payout** | что получает фотограф | только фотограф |

```
all-in  = ceil(base × 1.15 / 5) × 5        clientPriceWithFee()
payout  = base − base × commission(plan)   photographerPayoutFor()
площадка = all-in − payout
```

- Ставка сервисного сбора **15%**, округление **вверх до €5** — чтобы клиент
  видел цену (€345), а не арифметику (€343.85). Остаток округления остаётся
  площадке. `✔код` [src/lib/service-fee.ts](../src/lib/service-fee.ts)
- Комиссия зависит от плана: free **20%**, pro **15%**, premium **10%**.
  `✔код` [src/lib/stripe.ts:24](../src/lib/stripe.ts#L24)
- Планы стоят: free €0, pro €29, premium €59 в месяц. `✔код` stripe.ts:31
- **Клиенту нигде не показывается строка сбора.** Одна цена на всех
  поверхностях — каталог, страница пакета, чекаут, Stripe. Разошлись цифра на
  экране и списание — это тикет в поддержку.
- Группа **9+ человек** — надбавка **+50% на base**, до сервисного сбора.
  `✔код` stripe.ts:46
- **У оплаченной брони показывать сохранённый `payout_amount`, а не
  пересчитывать** — план фотографа мог смениться после оплаты. Пересчёт
  допустим только как прогноз для неоплаченной. `✔код` stripe.ts:56
- Слепая бронь считается наоборот, от итоговой суммы: `blindBaseFromTotal()`
  вытаскивает base из того, что заплатил клиент (€279 → €237.15), и уже к нему
  применяется комиссия плана того фотографа, которого назначили.
  `✔код` [src/lib/blind-booking/pricing.ts:284](../src/lib/blind-booking/pricing.ts#L284)

⛔ Никогда не делать `SELECT b.*` в ответ фотографу: в строке брони лежат
`total_price`, `platform_fee`, `service_fee` — всё то, чего он видеть не должен.

## 3. Бронь: два независимых статуса

`bookings` — **114 колонок**, и в ней **две разные колонки статуса**. Их путают,
и это стоило времени уже не раз.

Обе — **настоящие PG-enum'ы**, не varchar. Значения (`✔прод`, `pg_enum`):

- **`status` → `booking_status`**, 9 значений: `pending, confirmed, completed,
  cancelled, inquiry, delivered, disputed, refunded, unmatched`
- **`payment_status` → `payment_status`**, 5 значений: `pending, paid,
  refunded, failed, partially_refunded`

Они **ортогональны**: бронь бывает `confirmed` с `payment_status='failed'` (так
выглядит единственная итальянская). **«Оплачена» — это `payment_status`**;
админка и выручка считаются именно по нему (`admin/page.tsx:118`, `✔код`).

Enum — не varchar: новое значение добавляется через `ALTER TYPE`, и тогда же
правится `BookingStatus` в [src/types/index.ts](../src/types/index.ts).

### Путь брони

Канонический порядок для клиента (`BookingJourney.tsx:24`, `✔код`):

```
inquiry → pending → confirmed → completed → delivered
```

- **`pending` — дефолт колонки в базе** (`DEFAULT 'pending'::booking_status`,
  `✔прод`): любой INSERT, не назвавший статус явно, попадает сюда. Это не
  «ожидает оплаты» и не «ожидает ответа» — это «никто не сказал, какой статус».
  Плюс есть ручной перевод кнопкой в `BookingStatusButtons.tsx:62`.
- **`completed` = «съёмка состоялась»**, и ставит его сам фотограф кнопкой
  «Mark as completed» в дашборде. Кнопка заблокирована до даты съёмки
  ([PhotographerDashboardClient.tsx:2160](../src/app/%5Blocale%5D/dashboard/photographer/PhotographerDashboardClient.tsx#L2160), `✔код`).
- **`completed` — это пропуск к загрузке галереи**: страница доставки пускает
  только при статусе `completed` или `delivered` (`deliver/page.tsx:55`).
- **`delivered`** ставит сама доставка галереи, плюс разрешение диспута.
- `cancelled`, `disputed`, `refunded` — вне линии, в любой момент.

⚠️ **Ловушка при поиске по коду.** Статус приходит из тела PATCH-запроса
(`/api/bookings/[id]`, `const { status } = body`), а не пишется SQL-литералом.
Грепом `status = 'completed'` кажется, что состояние мёртвое — это неправда,
его ставит UI. Ищите `updateStatus("...")` и разбор `body`. Явной таблицы
разрешённых переходов в коде нет: их стережёт UI и проверки в ветках.

### Слепые брони

`blind_booking = true` — клиент купил слот, не выбирая фотографа. Следствия:

- **Стартовый статус — `unmatched`**, `photographer_id` = NULL
  (`concierge/blind-booking/accept/route.ts:21`, `✔код`). Любая статистика и
  любой JOIN по фотографу обязаны это учитывать, иначе слепые брони исчезают
  из отчётов.
- На `unmatched` висит **авто-возврат по крону** (`api/cron/auto-refund-blind`,
  ежечасно, по `auto_refund_at`): фотограф не назначен вовремя — деньги
  возвращаются автоматически.
- Доступность для слепых броней брать **нельзя** из календарей — они врут
  «свободно» (см. память `phototravel_mcp_channel`).

## 4. Фотограф: одобрение и видимость

- **`is_approved` = «виден в каталоге и его можно забронировать»** — не «прошёл
  модерацию». **308 вхождений в 88 файлах** (`✔код`, 14.08.2026): менять смысл
  нельзя, можно только заводить отдельный флаг рядом.
- Онбординг двухэтапный: сначала аппрув (виден), потом неделя на Stripe. Не
  успел — профиль скрывается: `stripe_deadline_at`, `stripe_hidden_at`,
  `stripe_onboarding_complete`, серия напоминаний `stripe_nudge_d1/d4/d6_sent`.
  `✔прод` (колонки), см. память `two_stage_onboarding`
- **`is_verified` — платная фича, а не решение админа.** Годовая подписка
  **€19** (Stripe product «Verified Badge»,
  [stripe/verified/route.ts:9](../src/app/api/stripe/verified/route.ts#L9)),
  доступная после подтверждения телефона по SMS
  (`dashboard/verification/phone` → `phone_verified`). Включает её вебхук по
  `checkoutType === "verified"`; отмена или протухание подписки гасит обратно
  в FALSE (`stripe/webhook/route.ts:509,1402,1482`, `✔код`). Админ может
  выставить руками — это override, а не основной путь.
  **Значит: тройной вес в выдаче (см. ниже) — купленный, а не заслуженный.**
- Прочие флаги: `is_featured`, `is_founding`, `is_test`, `early_bird_tier`,
  `plan`. `is_founding` и `early_bird_tier` **на комиссию не влияют** — в
  денежных путях (`lib/stripe.ts`) их нет вовсе; они дают вес в некоторых
  подборках (`business-showcase.ts`) и срок льготного плана, а комиссия всегда
  считается от `plan`. `✔код`
- **Выдача — взвешенная случайность, а не ранжирование.** Это сознательно, но об
  этом забывают всякий раз, обсуждая «продвижение». На главной
  ([page.tsx:242](../src/app/%5Blocale%5D/page.tsx#L242), `✔код`):

  ```sql
  ORDER BY CASE WHEN is_featured THEN 0 ELSE 1 END,          -- featured всегда сверху
           CASE WHEN is_featured THEN RANDOM()
                ELSE -LN(RANDOM()) / (is_verified ? 3.0 : 1.0)  -- verified втрое чаще
           END
  ```

  Ни просмотры, ни рейтинг, ни отзывы на порядок не влияют **никак**.
- **Фотограф без аватара в выдаче отсутствует — осознанно** (Алекс,
  14.08.2026: профиль без лица не продаёт, сначала фото). В WHERE стоит
  `u.avatar_url IS NOT NULL` (плюс `is_approved` и не-`is_test`), поэтому
  одобренный без фото не «внизу списка», а невидим. Это правило, не баг — не
  «чинить»; но при жалобе «меня не видно в каталоге» проверять первым делом.

## 5. Кто что видит

Два независимых правила маскировки, оба — про защиту площадки от обхода:

1. **Фамилии.** В видимом UI, в JSON-LD и в `alt` — только «Имя Б.»
   (`maskSurname()`). Полностью фамилия остаётся лишь в `<title>` и meta.
   Админка и координация после оплаты — без маскировки.
2. **Деньги.** См. §2: фотограф видит payout, клиент — all-in, base не видит
   никто.

## 6. Переписка

Треды **сквозные по паре (клиент, фотограф)**, а не по брони. Запросы скоупить
по `client_id + photographer_id`; скоуп по `booking_id` разрежет одну беседу на
куски.

## 7. Поля, которые врут

| Поле | В чём подвох |
|---|---|
| `bookings.total_price` | у слепых броней до и после 2026-07-08 значит разное; истина — `amount_received` из Stripe PI |
| `photographer_profiles.created_at` | не дата аппрува; аппрув брать из `admin_audit_log` по `entity_id` |
| `reviews.comment` | **не существует**; поле называется `text` |
| любой `NUMERIC` из pg | приходит **строкой**; `rating.toFixed()` падает — коэрцить `Number()` |
| `db/schema.sql` | мёртв, отстал от прода; смотреть боевую базу (`MARKETS.md §4.2`) |
| `visitor_sessions.country` | гео посетителя из `cf-ipcountry`, к рынку отношения не имеет |
| греп по SQL-литералам | статусы часто приходят из тела запроса (`const { status } = body`), а не пишутся строкой в SQL. «Никто не выставляет X» по грепу — почти всегда неправда; проверять UI и разбор `body` |

## 8. Оси «готово»

Правка почти никогда не одна. Перед тем как сказать «сделано», пройти оси —
пропущенная ось и есть «задача сделана наполовину»:

- [ ] **3 рынка** — код общий, правка уезжает всем; проверить, что для ES/IT это осмысленно
- [ ] **5 локалей** — ключи заводить во все `messages/*.json` сразу (иначе сырые пути в проде, см. CLAUDE.md)
- [ ] **веб + приложение** — паритет часто отстаёт; если не делаем в приложении, сказать это вслух
- [ ] **моб/десктоп** — в дашбордах два блока с одной логикой, чинить оба
- [ ] **три роли** — клиент / фотограф / админ видят одно и то же по-разному (и §2 запрещает показывать лишнее)
