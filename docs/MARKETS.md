# Рынки — как устроены и как завести новый

Один репозиторий, одна ветка `main`, **три прода**: Португалия, Испания, Италия.
Этот файл — про то, что общее для всех рынков. Факты конкретной страны живут в
своём файле: [SPAIN.md](SPAIN.md), [ITALY.md](ITALY.md). Португалия отдельного
файла не имеет — она и есть ветка по умолчанию.

> Этот файл вырос из `SPAIN.md`, который к августу 2026 описывал мир из двух
> стран, называя себя единственным источником правды. Италию подняли 09.08.2026,
> и она не была задокументирована нигде: я планировал деплой на две страны и не
> знал адреса третьего бокса. Разделено 12.08.2026.

## 1. Зафиксированные решения

Приняты явно, менять только осознанно.

| Решение | Значение | Дата |
|---|---|---|
| Кодовая база | **Один репозиторий, одна ветка `main`**. Никаких форков и веток по странам | 31.07.2026 |
| Инстансы | Отдельный сервер на страну. Различия — только в `.env` + country-пак | 31.07.2026 |
| Мультиарендность | **НЕТ.** Не резолвим страну по заголовку Host — она приходит из `COUNTRY` в env | 31.07.2026 |
| Аккаунты — ФОТОГРАФЫ | **Раздельные** в каждой стране. Профиль, выплаты и Stripe живут в одной | 31.07.2026 |
| Аккаунты — КЛИЕНТЫ | **Один вход, страны добавляются по мере надобности.** В приложении клиент листает любую страну без выхода из аккаунта; при первом действии за границей (бронь, сообщение) страна добавляется к аккаунту, и брони с чатами всех стран сходятся в одну ленту с флажками | 13.08.2026 |
| Базы данных | **Раздельные.** Колонка `country` заводится сразу — чтобы будущее слияние было копированием данных, а не редизайном схемы | 31.07.2026 |
| Stripe | **Свой аккаунт на рынок.** Connect — как в Португалии | 01.08.2026 |

**Точка пересмотра раздельности была «третья страна».** Она наступила
09.08.2026, и 13.08.2026 её пересмотрели — но только для КЛИЕНТОВ и только в
приложении. Фотографы остаются в одной стране: их профиль, выплаты и Stripe
привязаны к ней.

### Что «один вход» значит на самом деле (13.08.2026)

Общего пользователя между базами по-прежнему НЕТ. За единым входом стоят
отдельные строки в каждой стране, потому что базы раздельные:

- **Google/Apple** переносятся в один тап: аудитории OAuth намеренно общие для
  всех трёх деплоев, поэтому вторая страна опознаёт человека у самого
  провайдера, а не с наших слов.
- **Пароль** — одно подтверждение: хэш лежит в одной базе, открытый пароль мы
  не храним. Сначала пробуем вход (аккаунт мог быть заведён на сайте), потом
  регистрацию.
- **Связывание по email, который прислал клиент, запрещено везде** — это
  инвариант после захвата аккаунтов через OAuth (fca7859 / 178453f).
- Следствия, которые надо озвучивать честно: пароль и его сброс постранные,
  Stripe-профиль и сохранённая карта постранные, удаление данных по GDPR надо
  выполнять в каждой стране, где у человека есть строка.

Это не единый identity, а «портфель под одной лентой». Настоящий единый
identity (общий реестр или слияние баз) остаётся открытым — и сейчас в нём нет
нужды: клиентов, встречающихся больше чем в одной стране, на 13.08.2026 ровно
три, и все три — аккаунты Алекса.

### Почему не один процесс на несколько доменов

Резолв страны по Host потребовал бы переделки 203 route-хендлеров, module-level
синглтонов (`pool` в `db.ts`, stripe-клиент, кэши) и кэша ISR, который ключуется
по пути, а не по хосту. Месяцы работы ради экономии одного сервера. Отказались.

## 3. Что обязано быть раздельным

Общая ровно одна вещь — кодовая база. Всё остальное разное.

| Ресурс | Почему |
|---|---|
| ⛔ **Telegram-бот** | У бота ровно ОДИН вебхук. Если новый рынок выставит свой на чужой токен, он **молча отберёт вебхук** — уведомления умрут без единой ошибки в логах |
| База данных | Решение выше |
| R2-бакет | Свой бакет, свой публичный URL, свой CORS |
| SMTP | Свой ящик на своём домене. Слать письма рынка с чужого адреса нельзя ни по доставляемости, ни по смыслу |
| Google OAuth client | Новый клиент, не правка живого. Одного логина мало — см. §9 |
| `AUTH_SECRET` / `CRON_SECRET` | Свои |
| GA4 / GSC / Google Ads | Свои |
| Stripe | Свой аккаунт, вебхук и каталог товаров — см. §8 |
| Intercom | Своё пространство или `null`. Переиспользовать чужое нельзя — переписки смешаются в одном инбоксе |

### Stripe: почему аккаунт отдельный (решено 01.08.2026)

Вебхуки Stripe рассылаются на **все** эндпоинты аккаунта, поэтому общий аккаунт
означал бы, что каждый рынок получает события остальных, и нужен фильтр по
`metadata.country` в каждом обработчике. Плюс балансы и выплаты легли бы в одну
кучу без возможности разделить постфактум.

Отдельный аккаунт снимает обе проблемы и не стоит ничего. Фильтр по
`metadata.country` **не нужен** — не добавлять.

### 4.1. База системы

```bash
# swap — на 8 ГБ сборка Next проходит и без него, но запас нужен
fallocate -l 8G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# Node 20 — ровно как на проде PT (не 22, чтобы не ловить расхождение)
curl -fsSL https://deb.nodesource.com/setup_20.x | bash - && apt install -y nodejs
npm i -g pm2

# Postgres 16 — дефолт Ubuntu 24.04, совпадает с продом PT (16.14)
apt install -y postgresql postgresql-contrib nginx certbot python3-certbot-nginx
```

Спека боксов одинаковая: Hetzner CX33, 4 ядра / 8 ГБ / 80 ГБ, Ubuntu 24.04.
Свой ssh-ключ на рынок, чужие не переиспользовать.

### 4.2. База данных

**НЕ поднимать по `db/schema.sql`** — он мёртв (24 таблицы, нет
`admin_audit_log`, `business_inquiries`, `calendar_*`, `concierge_*` и других).
Схему берём с живого прода PT:

Сразу после этого:

1. завести пользователя и базу рынка;
2. добавить колонку `country` (`db/market-country-column.sql`) — `users`,

3. **владелец таблиц — приложенческий юзер, не `postgres`** (см. §5).

### 4.3. Каталоги и деплой

Зеркалим раскладку из §2. `deploy.sh` копируется с работающего бокса с заменой
путей и имён pm2.

ws-server — порт 3002. Файл лежит в `/var/www/<app>/`, `node_modules` там —
симлинк в каталог активного цвета, pm2-процесс `<app>-ws` с
`--cwd /var/www/<app>` (иначе не найдёт `.env`). `deploy.sh` копирует свежий
`ws-server.js` из собранного цвета и перезапускает процесс.

На Испании этот пункт пропустили при сборке 01.08 и заметили только 03.08: чат
не обновлялся без перезагрузки страницы, каждый `notifyUser()` уходил в пустоту,
слушать `pg_notify` было некому.

**⛔ Подмена порта в `deploy.sh` — по СТАРОМУ порту, а не по маске.**
`s|proxy_pass http://localhost:[0-9]*;|...|g` переписывает *каждый* `proxy_pass`
в файле, то есть первый же деплой уводит `/ws` с 3002 на порт приложения и
убивает чат.

### 4.4. Nginx и TLS

Свой vhost на домен + `www`, proxy_pass на активный порт.
`certbot --nginx -d <домен> -d www.<домен>`.

Пока домен не финальный — отдавать `noindex`.

### 4.5. Крон

Продублировать задачи с работающего бокса, заменив домен и секрет. Проверить,
что `CRON_SECRET` в URL — свой, а не скопированный.

**⛔ Не звать приложение по фиксированному порту.** blue-green чередует 3000 и
3001, а `curl -s` глотает ошибку молча. На Испании все 7 строк ходили на
`127.0.0.1:3000`, и пока был активен green, весь крон стучался в мёртвый порт —
за двое суток 113 запусков reminders вместо ~191.

Правильно: блок `listen 127.0.0.1:8090` с литералом
`proxy_pass http://localhost:3000`, который `deploy.sh` переписывает на активный
цвет; crontab ходит на 8090. Там же `proxy_read_timeout 600s` — иначе тяжёлые
прогоны `reminders` рубятся по таймауту.

### 4.6. ⛔ Бэкапы — в тот же день, что и сервер

**07.08.2026 испанский бокс был по ошибке ребилднут из консоли Hetzner вместо
итальянского. Диск затёрся; бэкапа не существовало ни одного — ни в Hetzner, ни
на Google Drive, ни на боксе PT. База Испании потеряна безвозвратно.** Причина
одна: при сборке бэкап-крон не продублировали, и в runbook про бэкапы не было
ни слова.

Скрипт в репозитории — `scripts/backup-db.sh`. Всё нужное берёт из `.env` рынка
и генерирует конфиг rclone сам.

```bash
# 1. Ключи в .env рынка (скопировать из .env работающей страны)
DB_BACKUP_R2_ACCESS_KEY_ID=...      # токен на бакет norteirabackups
DB_BACKUP_R2_SECRET_ACCESS_KEY=...
DB_BACKUP_BUCKET=norteirabackups
GDRIVE_TOKEN=...                    # вторая площадка
ENV_BACKUP_PASSPHRASE=...           # шифрование .env

# 2. Скрипты из репозитория
ln -sf /var/www/<app>-blue/scripts/backup-db.sh     /usr/local/bin/backup-db.sh
ln -sf /var/www/<app>-blue/scripts/check-backups.sh /usr/local/bin/check-backups.sh

# 3. Крон
0 3 * * * /usr/local/bin/backup-db.sh     /var/www/<app>/.env >> /var/log/db-backup.log 2>&1
0 9 * * * /usr/local/bin/check-backups.sh /var/www/<app>/.env >> /var/log/db-backup.log 2>&1
```

Требования, без которых это не бэкап:

1. **Две площадки.** Дамп на диск того же сервера не переживает ребилд — а
   ребилд и есть самый вероятный сценарий потери. Ночь успешна, только если
   хотя бы одна копия прочиталась обратно; если ушла одна из двух — всё равно
   алерт, потому что одна копия это дорога к нулю.
2. **Проверять факт чтения, а не запуска и даже не заливки.** Скрипт скачивает
   залитое обратно, разжимает и убеждается, что внутри заголовок настоящего
   дампа. Дамп меньше 100 КБ отвергается, чтобы «успешный» пустой не затёр
   хорошие копии.
3. **Сторож снаружи.** `check-backups.sh` смотрит папки ВСЕХ стран с ЛЮБОГО
   бокса. Здоровый лог на Португалии ничего не говорил про Испанию — это и была
   слепая зона. «Бэкапов не найдено» — тревога, а не «всё чисто».
4. **Bucket Lock на `norteirabackups`** — 30 дней, без префикса.
   ⛔ Не `Indefinite` — чистка старше 90 дней перестанет работать.
   ⛔ На бакеты с ФАЙЛАМИ лок не ставить: ZIP доставки пишется в стабильный ключ
   (`build-zip.ts`) и пересобирается, лок это сломает.
5. **Восстановление проверять до того, как оно понадобится** — безопасно, дамп
   разворачивается в ОТДЕЛЬНУЮ базу:

   ```bash
   rclone --config <conf> --s3-disable-checksum cat \
     r2:norteirabackups/<market>/<файл>.sql.gz | gunzip > /tmp/restore.sql
   sudo -u postgres psql -q -c 'CREATE DATABASE restoretest'
   sudo -u postgres psql -q restoretest < /tmp/restore.sql
   # сверить count(*) по users / bookings / reviews / messages / delivery_photos
   sudo -u postgres psql -q -c 'DROP DATABASE restoretest'
   ```

   Проведено 07.08.2026 на Португалии: 0 ошибок, 63 таблицы, счётчики сошлись
   до строки. Повторять после крупных миграций.
6. **`.env` бэкапится зашифрованным.** Ребилд уносит все секреты. Пишется в
   `norteirabackups/env/<market>/` под AES-256; фраза в `.env` для шифрования и
   в парольном менеджере Алекса для расшифровки. ⛔ В открытом виде нельзя: один
   S3-ключ тогда отпирает и бэкапы, и Stripe, и базу.

### 4.7. ⛔ Регрессионный тест Португалии

Любая массовая автозамена по общему коду обязана проверяться на Португалии
до деплоя. Скрипт сравнивает **инварианты**, а не байты: title, description,
og-теги, canonical, hreflang, наличие партнёрского блока / соцсетей / бейджей,
счётчик бренда и домена, строка юрлица, состав переключателя языков, число H1,
URL и хосты сайтмэпа. Побайтовый диф не годится — главная выбирает фотографа
случайно на каждый запрос.

Проверка 2026-08-01 нашла **три регрессии**, ни одну нельзя было увидеть глазами:

1. **`href="mailto:country.supportEmail"`** — массовая замена подставила
   выражение строкой. Подпись рендерилась верно, но клик открывал почтовый
   клиент с адресом «country.supportEmail». Шесть файлов, все рынки.
2. **Сайт компании в блоке контролёра данных подменился регулятором** — правка
   ссылки зацепила соседнюю строку «Website».
3. **Главная потеряла из `sameAs` профиль Google Business и TikTok** — у неё
   свой список профилей, отличный от корневого макета.

## 5. Схема и миграции

### ⚠ Миграции — на ВСЕ базы

`001_payout_details.sql` был накатан только на Испанию, а общий код читал
`pp.payout_iban` безусловно. Выкатка на Португалию без миграции положила бы
дашборд фотографа и подтверждение брони у каждого португальского фотографа.

### Владелец таблиц — приложенческий юзер (выровнено 2026-08-09)

На ES и IT все 62 таблицы, 5 секвенций и вьюха принадлежали `postgres`, а
приложение ходит под своим юзером. `psql "$DATABASE_URL" -f миграция.sql`
работал на Португалии и падал на двух других с `ERROR: must be owner of table
users` — причём права проверяются ДО `IF NOT EXISTS`, так что даже идемпотентная
миграция валилась, и по логу это неотличимо от настоящей поломки схемы.

Выровнено под Португалию (владелец = юзер из `DATABASE_URL`). Поднимаешь
четвёртый рынок — следи, чтобы схему заливал приложенческий юзер.

### Колонка рынка `country`

`db/market-country-column.sql` — `users`, `bookings`, `photographer_profiles`,
`VARCHAR(2) NOT NULL DEFAULT '<рынок>'`. Страховка из §1. Кода, читающего эти
колонки, нет ни на одном рынке — миграция сознательно no-op.

⚠️ Не путать с `visitor_sessions.country` и `concierge_chats.country`: это
гео-страна посетителя из `cf-ipcountry`, к рынку отношения не имеет.

## 6. Деплой

```
Мак: один репо, одна ветка main
 ├── rsync → photoportugal-incoming → deploy.sh → PT
 ├── rsync → photospain-incoming    → deploy.sh → ES
 └── rsync → photoitaly-incoming    → deploy.sh → IT
```

Git на серверах нет — код заливается rsync'ом с ноутбука.

### ⛔ Исключения rsync

`.env` **и `.env.local`**. Next грузит `.env.local` раньше `.env`, поэтому
локальный файл с Мака, уехавший на сервер, молча подменит настройки — включая
`DATABASE_URL`. Рынок начнёт писать в чужую базу, и никакой ошибки видно не
будет.

```bash
rsync -a --delete \
  --exclude=node_modules --exclude=.next --exclude=.git \
  --exclude=.env --exclude=.env.local \
  --exclude=uploads --exclude=google-credentials.json \
  /Users/alex/projects/photoportugal/ <host>:/var/www/<app>-incoming/
```

### Порядок раскатки

Код общий, значит любая правка ради одного рынка прилетит остальным. Поэтому:
**сначала малые рынки (ES, IT), убедиться, что живы, потом PT.**

⚠️ **Цвет после деплоя брать из вывода `deploy.sh`, а не угадывать.** Дважды
12.08.2026 я ждал не тот цвет и один раз преждевременно решил, что фикс уже в
проде. Проверять результат по базе и по живой странице, а не по факту запуска.

## 7. Что различается в коде

### Country-пак

Всё страновое — в `src/lib/country.ts`: бренд, домен, base URL, from-адрес,
`supportEmail`, `areaServed`, `countryName`/`countryIn` (склонения и предлоги),
локали, `nativeLocale`/`languageLabel`, часовой пояс, юрлицо, `intercomAppId`,
`dialCode`.

⛔ **Ничего странового не хардкодить в письмах, SMS, пушах, Telegram и Stripe.**
Это уже стреляло дважды: 12.08.2026 нашлось 30 мест, где всем рынкам писали
«Photo Portugal» — включая письмо об одобрении профиля, строку чаевых в выписке
по карте и имена скачиваемых файлов `PhotoPortugal_*.jpg`. Для стран брать
`country.countryIn.<locale>`: по-французски «au Portugal», но «en Espagne».

### ⛔ Переключатель страны — только `NEXT_PUBLIC_COUNTRY`

Для всего, что может дойти до браузера, страну читать из `NEXT_PUBLIC_COUNTRY`,
а не из `COUNTRY`. `Header.tsx`, `Footer.tsx`, админский `LocationsManager.tsx` —
клиентские компоненты и импортируют `locations-data`. Переменная без префикса
вырезается из браузерного бандла → `undefined` → ветка по умолчанию → **чужие
города в собственной шапке**, без единой ошибки в логах.

В `.env` заведены обе. Португалия везде остаётся веткой по умолчанию.

### Датасет локаций

`src/lib/locations-data.ts` экспортирует `locations`, переключаясь по
`NEXT_PUBLIC_COUNTRY` между `locationsPT`, `locationsES` (`locations-data-es.ts`)
и `locationsIT` (`locations-data-it.ts`).

`nearbyLocationsMap` и `locationFaqs` в том же файле — **только португальские
слаги**. На других рынках они просто не находятся (деградация мягкая: нет блока
похожих локаций и нет FAQ на странице локации).

## 8. Stripe

### Страна платформы ≠ страна фотографа

Проверено экспериментально 2026-08-01, не по документации: с ключа платформы,
зарегистрированной в PT, создан connected-аккаунт со страной ES, после чего
удалён. Каждый фотограф — отдельный connected-аккаунт, который верифицирует
**себя**: имя, дата рождения, адрес, свой IBAN, своё принятие условий.

⚠️ Это ответ Stripe, а не бухгалтера. Должно ли португальское ИП принимать
деньги за услуги в другой стране — вопрос НДС и места оказания услуги. Stripe не
заблокирует, налоговая может иметь мнение.

**Ключевая деталь:** в `POST /api/stripe/connect` страна создаваемого аккаунта
берётся из country-пака (`country.code.toUpperCase()`), а не из литерала `"PT"`.
Литерал там был — каждый испанский фотограф получил бы португальский аккаунт, и
Stripe попросил бы у него португальский IBAN.

### Каталог товаров — свой у каждого инстанса

⛔ **Аккаунты разные, значит price ID одного рынка в другом не существуют.** Это
стоило Испании всех подписок: фолбэком были захардкожены два португальских price
ID, и любой апгрейд падал с `No such price`, а наружу отдавалось `Invalid
action` — симптом без связи с причиной. Фолбэк удалён, теперь 503 и лог с именем
переменной.

`STRIPE_PRO_PRICE_ID` и `STRIPE_PREMIUM_PRICE_ID` — в `.env` рынка. Featured и
Verified в env НЕ кладём: роуты ищут товар по `metadata.type` и создают сам,
если не нашли. Поэтому название товара обязано идти через `country.brand` —
иначе первый покупатель самозародит товар «Photo Portugal — …» в чужом аккаунте.

### ⚠️ Публичный профиль аккаунта правится ТОЛЬКО руками

`business_profile.url` и `support_email` Stripe показывает клиенту на странице
оплаты, в письме с чеком и фотографу при онбординге. Через API не исправить:
`POST /v1/accounts/{id}` отвечает `You cannot use this method on your own
account`.

Dashboard → Settings → Business → Public details. Проверка:

```bash
curl -s https://api.stripe.com/v1/account -u "$STRIPE_SECRET_KEY:" \
  | python3 -c "import sys,json;b=json.load(sys.stdin)['business_profile'];print(b['url'],b['support_email'])"
```

## 9. Google OAuth: календарь настраивается отдельно от логина

Ловушка в том, что логин работает и всё выглядит настроенным, а календарь
отдаёт «Access blocked: This app's request is invalid». `REDIRECT_URI`
собирается из `country.baseUrl`, то есть на каждом рынке свой.

Что должно быть в проекте нового рынка:

1. **APIs & Services → Library → Google Calendar API → Enable.** Пока API
   выключен, скоупов Calendar нет даже в списке на экране выбора скоупов.
2. **Скоуп `https://www.googleapis.com/auth/calendar.readonly`** на экране
   согласия. Он sensitive — требует верификации с обоснованием и демо-видео.
3. **Authorized redirect URIs — ДВА, не один:**
   - `https://<домен>/api/auth/callback/google` — вход на сайт;
   - `https://<домен>/api/calendar/google/callback` — подключение календаря.

Проверять без браузера:

```bash
curl -sL -G "https://accounts.google.com/o/oauth2/v2/auth" \
  --data-urlencode "client_id=<client_id>" \
  --data-urlencode "redirect_uri=https://<домен>/api/calendar/google/callback" \
  --data-urlencode "response_type=code" \
  --data-urlencode "scope=https://www.googleapis.com/auth/calendar.readonly openid" \
  -o /tmp/r.html -w "%{url_effective}\n"
grep -oE "Error 4[0-9]+[^<]*|invalid_scope" /tmp/r.html
```

`Error 400: redirect_uri_mismatch` — URI не заведён; `v3/signin/identifier` —
конфиг рабочий.

**Пока идёт верификация** приложение пускает только аккаунты из Test users.
Добавлять туда нужно аккаунт, где лежит календарь, а не тот, которым фотограф
логинится на сайт.

## 10. Telegram

Тем группы (Topics) задаются переменной окружения, а не в коде — thread-ID между
странами не переносятся, отправка падает с `message thread not found`:

```
TELEGRAM_CHAT_ID=-100...
TELEGRAM_TOPIC_IDS={"bookings":2,"daily_digest":3,"photographers":4,...}
```

Португалия переменную не задаёт и использует зашитые значения.

⚠️ **Конвертация группы в форум меняет `chat_id`.** Старый ID начинает отдавать
`400 Bad Request: group chat was upgraded to a supergroup chat`, и **все**
уведомления молча перестают доходить. Новый ID лежит в ответе Telegram в
`parameters.migrate_to_chat_id`.

Проверка доставки — таблица `notification_logs`.

## 11. Проверка на утечки Португалии

`node scripts/audit-country-leaks.mjs` — гонять перед каждым деплоем не-PT рынка.

Первая версия проверки **врала**: рапортовала «0 страниц с остатками», пока на
живом сайте в FAQ висел `info@photoportugal.com`, на `/try-yourself` светились
16 сырых ключей, а во французском 107 строк читались как «au Espagne». Причины:
сравнение было регистрозависимым; из каждой страницы вычиталось одно
«разрешённое» вхождение, поэтому страница ровно с одной утечкой считалась
чистой; искались только топонимы, поэтому `+351` и `PHOTO PT` были невидимы.

Теперь исключения — **явный список ключей, никогда не счётчик**.

**Живой скан обязателен отдельно** и должен смотреть `<meta>` и JSON-LD: скан по
видимому тексту их не видит, а именно там жило `"Barcelona, Portugal"` в
`TouristDestination`.

## 12. Грабли, общие для всех рынков

1. **`db/schema.sql` мёртв** — см. §4.2.
2. **`scripts/deploy.sh` в репозитории устарел** — тычет в старый IP и делает
   `git pull` на месте. Реальный скрипт живёт на сервере, `/var/www/deploy.sh`.
3. **`docs/ARCHITECTURE.md` устарел** — описывает DigitalOcean и локальное
   хранение файлов. Не ориентироваться.
4. **i18n**: `useTranslations("ns")` без ключей в `messages/*.json` рендерит
   сырые пути ключей в проде, и `|| "fallback"` это не ловит. Ключи заводить во
   все локали одновременно с компонентом. См. CLAUDE.md.
5. **⚠️ Значения с `#` в `.env` обрезаются.** Загрузчик Next (`@next/env` поверх
   dotenv) считает `#` началом инлайн-комментария. Из-за этого Испания **не
   отправляла писем с самого запуска**: пароль `Diaspora07##` обрезался до
   `Diaspora07`, SMTP возвращал `535 authentication failed`, а проверка через
   shell проходила, потому что `cut -d= -f2-` отдаёт строку целиком.

   **Правило: любое значение с `#`, пробелом, `$` или кавычками — только в
   двойных кавычках.** Проверять тем же загрузчиком, что и приложение:

   ```bash
   cd /var/www/<app>-blue && node -e '
   const { loadEnvConfig } = require("@next/env");
   loadEnvConfig(process.cwd(), false);
   console.log("SMTP_PASS длина:", (process.env.SMTP_PASS||"").length);
   '
   ```

   Родственник проблемы с bcrypt-хэшами: `$` гибнет в shell-кавычках, `#` — в
   dotenv. Оба раза значение молча укорачивается, и ошибка выглядит как
   «неверный пароль». Сломанные письма видно только в `notification_logs`
   (`channel='email'`, `status='failed'`) — форма отдаёт 200.
6. **Логи pm2 и крона накопительные.** Перед замером `pm2 flush <app>-<color>`.
   ⚠️ `grep -c` по крон-логу врёт: вывод пишется без переносов строк, считать
   только `grep -o … | wc -l`.
