Второй инстанс на той же кодовой базе, для испанского рынка.
Заведён 2026-07-31.

**Статус на 2026-08-01: адаптация завершена, оба сайта проверены.**

Аудит Испании: **0 из 23 страниц** содержат остатки Португалии (кроме строки
юрлица, которая обязана быть португальской). Регрессионный тест Португалии:
**21 из 21 страницы** рендерят ровно то же, что до правок.

Готово: сервер (Node 20.20.2, Postgres 16.14, nginx, pm2 + logrotate — версии

Этот файл — единственный источник правды по Испании. Всё, что отличается от
Португалии, должно быть описано здесь, а не жить в голове.

## 1. Зафиксированные решения

Приняты явно, менять только осознанно.

| Решение | Значение | Дата |
|---|---|---|
| Кодовая база | **Один репозиторий, одна ветка `main`**. Никаких форков и веток по странам | 31.07.2026 |
| Инстансы | Отдельный сервер на страну. Различия — только в `.env` + country-пак | 31.07.2026 |
| Мультиарендность | **НЕТ.** Не резолвим страну по заголовку Host — она приходит из `COUNTRY` в env | 31.07.2026 |
| Аккаунты | **Раздельные** в каждой стране. Модель — портфель локальных брендов, не глобальный маркетплейс | 31.07.2026 |
| Базы данных | **Раздельные.** Колонка `country` заводится сразу (все строки `es`) — чтобы будущее слияние было копированием данных, а не редизайном схемы | 31.07.2026 |
| Точка пересмотра | Третья страна. При двух инстансах раздельность не болит | — |
| Stripe Connect | **Используем, как в Португалии.** Платформа PT, фотографы — испанские connected-аккаунты (см. §6.2, §15) | 01.08.2026 |
| Домен | `photospain.co`. `photospain.com` занят, владелец недоступен. Запасной постоянный бренд — `fotospain.com` (€431) | 31.07.2026 |

### Почему не один процесс на два домена

Резолв страны по Host потребовал бы переделки 203 route-хендлеров, module-level
синглтонов (`pool` в `db.ts`, stripe-клиент, кэши) и кэша ISR, который ключуется
по пути, а не по хосту. Месяцы работы ради экономии одного сервера. Отказались.

На Португалии та же схема с кастомным доменом `files.photoportugal.com`.

Токен намеренно ограничен правами **Object Read & Write** на один бакет — это
правильно с точки зрения безопасности, но означает, что **CORS через S3 API он
поставить не может** (`GetBucketCors` → AccessDenied). Ставить руками в дашборде:
R2 → бакет `photospain` → CORS Policy → Add:

```json
[
  {
    "AllowedOrigins": [
      "https://photospain.co",
      "https://www.photospain.co",
      "http://localhost:3000",
      "http://localhost:3001"
    ],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

Без CORS браузер не сможет заливать файлы по presigned-ссылкам напрямую, то есть
**портфолио фотографа не загрузится** — это обязательный шаг онбординга.

### Почта

> ⚠️ **Порт 587, не 465.** Hetzner блокирует исходящие **465 и 25** на этом
> сервере (проверено: с Мака 465 открыт, с бокса — таймаут). Открыт только 587,
> то есть STARTTLS. В `.env` стоит `SMTP_PORT=587`; `src/lib/email.ts` это
> переваривает сам (`secure: SMTP_PORT === 465`). В `scripts/cron.ts` то же
> самое было захардкожено как `secure: true` — исправлено 2026-08-01 вместе с
> удалением португальских фолбэков (см. §7). Проверено реальной отправкой.

- Ящик: `info@photospain.co` на Migadu
- Пароль — **только** в `/var/www/photospain/.env` на сервере (chmod 600).
  В git не коммитить ни при каких обстоятельствах.
- Нужны DNS-записи Migadu на домене: MX, SPF, DKIM, DMARC. Без них письма
  фотографам будут падать в спам, а онбординг стоит на письмах.

## 3. Что обязано быть раздельным

Общая у двух проектов ровно одна вещь — кодовая база. Всё остальное разное.

| Ресурс | Почему |
|---|---|
| ⛔ **Telegram-бот** | У бота ровно ОДИН вебхук. Если Испания выставит свой на токен PT, он **молча отберёт вебхук у Португалии** — уведомления умрут без единой ошибки в логах. Нужен отдельный бот |
| База данных | Решение выше |
| R2-бакет | Свой бакет, свой публичный URL, свой CORS |
| SMTP | Свой ящик на своём домене. Слать испанские письма с адреса photoportugal.com нельзя ни по доставляемости, ни по смыслу |
| Google OAuth client | Новый клиент, а не правка живого PT-шного |
| `AUTH_SECRET` / `NEXTAUTH_SECRET` | Свои |
| `CRON_SECRET` | Свой |
| GA4 / GSC / Google Ads | Свои |
| Stripe | На старте на Испании Stripe нет вообще — ключ не ставим, вебхук не заводим |

### Stripe на будущее

Когда откроется клиентская часть, платежи пойдут через то же португальское
юрлицо, то есть **один аккаунт Stripe на два инстанса**. Вебхуки Stripe
рассылаются на все эндпоинты аккаунта — значит Испания начнёт получать события
Португалии и наоборот. Понадобится:

1. класть `country` в `metadata` при создании PaymentIntent / Checkout Session;
2. в начале обработчика вебхука отбрасывать события с чужой `metadata.country`;
3. дополнительно — игнорировать событие, если брони нет в локальной базе.

Пока Stripe не подключён, этой проблемы не существует. Не подключать раньше времени.

## 5. Деплой

```
Мак: один репо, одна ветка main
 ├── rsync → photoportugal-incoming → deploy.sh → PT
 └── rsync → photospain-incoming    → deploy.sh → ES
```

Git на серверах нет — код заливается rsync'ом с ноутбука.

### ⛔ Исключения rsync

`.env` **и `.env.local`**. Next грузит `.env.local` раньше `.env`, поэтому
локальный файл с Мака, уехавший на сервер, молча подменит настройки — включая
`DATABASE_URL`. Испания начнёт писать в базу Португалии, и никакой ошибки при
этом видно не будет. Исключение зашито прямо в скрипт деплоя, чтобы не зависеть
от того, какую команду набрали руками.

### Порядок раскатки

Код общий, значит любая правка ради Испании прилетит в Португалию при следующем
деплое. Поэтому: **сначала ES, убедиться, что живо, потом PT.**

## 6. Что различается в коде

### 6.1. Country-пак

Всё, что зависит от страны, живёт в одном модуле и выбирается по `COUNTRY=es`:
бренд, домен, base URL, from-адрес, локали, часовой пояс, юрлицо, режим выплат.

### 6.2. Выплаты — Stripe Connect, как в Португалии

⚠️ **Ручной режим выплат удалён 2026-08-01.** Он существовал ровно неделю и
строился на неверной посылке: что португальская платформа не может подключать
испанских фотографов. Может — см. §15. Страна платформы ограничивает только
сам аккаунт платформы, а у каждого connected-аккаунта своя страна, своя
верификация личности и свой банковский счёт.

Удалён, а не выключен флагом. Спящая вторая ветка выплат — это код, который
никто не выполняет, а значит никто и не заметит, как он протухнет; ровно этот
класс ошибок уже стоил нам недели на утечках Португалии.

Что было убрано: экран ввода IBAN, `/api/dashboard/payout-details`, вкладка
ручных выплат в админке, `/api/admin/manual-payouts`, поле `payoutMode` в
country-паке и ветка `isManualPayout` в `src/lib/payout.ts`.

Колонки `payout_iban` и соседние остались в обеих базах: их никто не читает,
а DROP COLUMN на живом проде ради чистоты — риск без выгоды.

**Ключевая деталь при подключении:** в `POST /api/stripe/connect` страна
создаваемого аккаунта берётся из country-пака (`country.code.toUpperCase()`),
а не из литерала `"PT"`. Литерал там был, и никто из вызывающих страну не
передавал — то есть каждый испанский фотограф получил бы **португальский**
connected-аккаунт, и Stripe попросил бы у него португальский IBAN.

Connect остаётся жёстким гейтом минимум в 6 местах, и теперь это правильно для
обоих рынков:

- `src/app/(app)/admin/page.tsx` — очередь на модерацию требует
  `stripe_account_id IS NOT NULL AND stripe_onboarding_complete = TRUE`
- `src/app/api/bookings/[id]/route.ts` — приём брони
- `src/app/api/dashboard/earnings/route.ts` — страница заработка
- `src/app/api/cron/reminders/route.ts` — напоминания

Определение «фотографу можно платить» живёт в одном месте —
`payoutReadySql()` / `isPayoutReady()` в `src/lib/payout.ts`.

  были переписаны

**Проверка:** страница не должна содержать «Conecte Stripe / Connect Stripe /
Stripe verbinden / Connectez Stripe». Три оставшихся упоминания Stripe на
странице для фотографов — правильные, они про оплату клиентом.

### 6.3b. Герой главной при пустом ростере

`HeroSingleVariant` строится вокруг живого фотографа и обёрнут в
`{heroPhotographer && …}` — в новой стране запрос пуст, и герой не рендерился
вовсе: страница открывалась сразу секцией ценностного предложения.

`BrandHero` закрывает этот слот: та же весовая категория (крупное фото, летний
оффер, одна главная кнопка), но **никаких заявлений о ростере** — ни имени, ни
рейтинга, ни счётчика. Как только появится первый одобренный фотограф,
управление возвращается обычному герою.

⚠️ **Без `<h1>`.** H1 страницы живёт в секции ниже. Первая версия повторяла там
заголовок и абзац дословно — страница показывала один и тот же текст дважды
подряд. Тексты берутся из существующего неймспейса `heroSingle`, чьи ключи есть
во всех пяти локалях.

### 6.3c. Getting started: переведён впервые, для ОБЕИХ стран

Страница первых шагов фотографа была захардкожена по-английски и не переводилась
никогда и нигде — португальские фотографы читали её по-английски с запуска.
Вынесена в неймспейс `gettingStarted`, 19 ключей × 5 локалей, переводы написаны

существовать во всех пяти локалях, иначе next-intl отрендерит сырой путь.

### 6.4. ⛔ Переключатель страны — только `NEXT_PUBLIC_COUNTRY`

Для всего, что может дойти до браузера, страну читать из
**`NEXT_PUBLIC_COUNTRY`**, а не из `COUNTRY`.

`Header.tsx`, `Footer.tsx` и админский `LocationsManager.tsx` — клиентские
компоненты, и они импортируют `locations-data`. Переменная без префикса
`NEXT_PUBLIC_` вырезается из браузерного бандла, то есть на клиенте будет
`undefined`, тернарник уйдёт в ветку по умолчанию, и **испанский сайт покажет
португальские города в собственной шапке** — без единой ошибки в логах.

В `.env` заведены обе: `COUNTRY=es` для серверного кода и `NEXT_PUBLIC_COUNTRY=es`
для изоморфного.

Португалия везде остаётся веткой по умолчанию: отсутствующее или неизвестное
значение → сегодняшнее поведение.

## 12. Telegram — группа с темами (Topics)

Группа переведена в форум **2026-08-01**. Два подвоха, оба уже сработали:

1. **Конвертация меняет chat_id.** Обычная группа `-5309089216` стала
   супергруппой `-1004479581734`. Старый ID начинает отдавать
   `400 Bad Request: group chat was upgraded to a supergroup chat`, и **все**
   уведомления молча перестают доходить. В ответе Telegram есть
   `parameters.migrate_to_chat_id` — новый ID берётся оттуда.

2. **Thread-ID тем не переносятся между странами.** У Португалии свои номера
   (alerts=220, stripe=361, concierge=442), в испанской группе их нет —
   отправка падает с `message thread not found`.

Поэтому номера тем задаются переменной окружения, а не в коде:

```
TELEGRAM_CHAT_ID=-1004479581734
TELEGRAM_TOPIC_IDS={"bookings":2,"daily_digest":3,"photographers":4,"match_requests":5,"clients":6,"messages":7,"alerts":8,"stripe":9,"concierge":10}
```

Португалия переменную не задаёт и продолжает использовать зашитые значения.
`sendTelegram` теперь печатает в лог, что именно случилось (миграция чата или
несуществующая тема), а не безликое `HTTP 400`.

Темы создаются ботом: `createForumTopic` (бот должен быть админом с
`can_manage_topics`). Проверка доставки — таблица `notification_logs`.

## 13. Проверка на утечки Португалии

`node scripts/audit-country-leaks.mjs` — гоняется перед каждым деплоем Испании.

Первая версия этой проверки **врала**: рапортовала «0 страниц с остатками», пока
на живом сайте в FAQ висел `info@photoportugal.com`, на `/try-yourself`
светились 16 сырых ключей, а во французском 107 строк читались как «au Espagne».
Три причины, каждая закрыта:

- сравнение было регистрозависимым, поэтому `photoportugal.com` не совпадал с
  «Portugal»;
- из каждой страницы вычиталось одно «разрешённое» вхождение (в футере
  реквизиты португальского ИП) — страница ровно с одной утечкой считалась
  чистой. Теперь исключения — **явный список ключей**, никогда не счётчик;
- искались только топонимы, поэтому `+351` и `PHOTO PT` были невидимы.

Проверка закрывает шесть классов: наследование из базовой локали, Португалия
внутри испанского слоя, отсутствующие ключи (next-intl рисует сырой путь на
экране), слаги локаций, копирайт зашитый в country-aware компонентах, и
английское «Spain» внутри неанглийских полей датасетов.

**Живой скан обязателен отдельно** и должен смотреть `<meta>` и JSON-LD: скан по
видимому тексту их не видит, а именно там жило `"Barcelona, Portugal"` в
`TouristDestination` — то, что индексирует Google.

## 14. Stripe — живой режим

Аккаунт **отдельный** от португальского: `acct_1TzfRtGelEPoV4hO` (PHOTO SPAIN)
против `acct_1QmGoQGU0seq3XOV` (PHOTO PORTUGAL). Балансы, выплаты и вебхуки
независимы — это проверено через `/v1/account` обоими ключами до включения
живых ключей. Если бы аккаунт оказался общим, платежи двух стран легли бы в
один баланс, и разделить их постфактум было бы нечем.

Активирован 2026-08-01: `charges_enabled: true`, `payouts_enabled: true`,
`currently_due` пусто.

Вебхук `we_1Tzgb0GelEPoV4hOXNhCZJcF` → `https://photospain.co/api/stripe/webhook`,
21 событие (весь набор, который разбирает роут). Подпись проверяется — POST с
поддельным `stripe-signature` отдаёт `400 Invalid signature`.

Оплата идёт через **серверные Checkout Sessions** с редиректом на страницу
Stripe. `loadStripe` и `@stripe/stripe-js` в коде не используются, поэтому
`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` в клиентский бандл не попадает — это
нормально, а не признак незавершённой сборки. Живой режим подтверждён созданием
сессии: `cs_live_…`, `livemode: true`.

Connect для Испании включён (проверено: `/v1/accounts` на живом ключе
отвечает). Тот же аккаунт принимает деньги от клиентов и выплачивает
фотографам — как в Португалии.

## 15. Stripe Connect: страна платформы ≠ страна фотографа

Проверено экспериментально 2026-08-01, не по документации: с ключа платформы,
зарегистрированной в **PT**, создан connected-аккаунт со страной **ES**
(`country: ES`, `default_currency: eur`), после чего удалён.

Значит документ Кати ограничивает только идентификацию **самой платформы** —
это разовая процедура, уже пройденная. Каждый фотограф — отдельный connected-
аккаунт, который верифицирует **себя**: имя, дата рождения, адрес,
`external_account` (свой испанский IBAN) и собственное принятие условий Stripe.
В `currently_due` испанского аккаунта не было ни одного поля про владельца
платформы.

То есть техническое препятствие, из-за которого для Испании выбрали ручные
выплаты, **отсутствует**. Connect для испанских фотографов работает.

⚠️ Но это ответ Stripe, а не бухгалтера. Отдельный вопрос — должно ли
португальское ИП принимать деньги за услуги, оказанные в Испании испанскими
исполнителями (НДС, место оказания услуги, счета). Stripe это не заблокирует,
налоговая может иметь мнение. Решение за Алексом и бухгалтером, не за кодом.

Решение принято 01.08.2026: Испания переведена на Connect, ручной режим удалён (§6.2).
